单机数据服务
============

同一台机器上同时运行多个 hikyuu 进程（如 Jupyter 研究、策略回测、数据采集），且它们使用
**相同的数据目录**（``hikyuu.ini`` 中 ``[hikyuu]`` 节的 ``datadir``）时，hikyuu 会在进程间
自动协商出一份共享的数据服务：

* 第一个启动的进程竞选成为 **数据服务主进程（Master）**，照常加载全部数据，并对外提供
  证券基础信息、板块、K 线等查询服务；
* 其后启动的进程自动成为 **客户端（Client）**，不再重复预加载 K 线，数据取自 Master
  发布的 **共享内存快照**，或经 **IPC 请求** 向 Master 获取。

效果：只有第一个进程承担耗时的预加载与全部内存开销，后续进程的启动时间与内存占用大幅下降，
且各进程看到的数据保持一致。

.. note::

    协商以 ``datadir`` 为粒度（服务地址与文件锁名均由 ``datadir`` 的哈希派生），
    使用不同 ``datadir`` 的进程各自独立竞选 Master、互不干扰。

    本机制与行情采集服务（``quotation_server``）是两条相互独立的链路，互不干扰。

.. warning::

    共享内存段名与其记录文件（``hikyuu_ks.last`` / ``hikyuu_bi.last``）为全局固定，未按
    ``datadir`` 隔离。因此修改配置中的 ``datadir`` 后，若之前以旧 ``datadir`` 启动的进程
    **仍在运行**，新旧两个 Master 会共用同一份段记录文件：后启动者发布快照时会依记录清理掉
    先前 Master 正在使用的共享内存段，导致其之后新接入的客户端无法命中快照、退化为 IPC
    请求（数据仍然正确、已有客户端不受影响，仅新客户端延迟升高）。实际使用中 ``datadir``
    一般固定不变，故影响有限；如需切换 ``datadir``，建议先关闭所有以旧 ``datadir`` 运行的
    hikyuu 进程，再启动新配置的进程。

工作原理
--------

1. **主从选举**：进程初始化时先尝试连接已存在的服务；连接不上则竞争系统临时目录下的
   ``hikyuu_kdata_server_{hash}.lock`` 文件独占锁，抢到者为 Master，抢不到者说明对方正在
   启动中，按 500 毫秒间隔重试 20 次，仍失败则降级为独立模式运行（行为与本功能引入之前
   完全一致）。
2. **等待就绪**：客户端连接后轮询 Master 的加载进度。Master 在基础数据（证券列表、市场、
   证券类型、节假日、板块等）加载完毕即对外提供服务，**不等待 K 线预加载完成**；
   客户端的等待上限由 ``kdata_server_wait_timeout`` 控制。
3. **关闭客户端预加载**：客户端会把自身全部 K 线类型的预加载关闭（仅内存中生效，
   不修改配置文件），改由数据服务提供。
4. **共享内存快照**：Master 完成 K 线预加载后，把已预加载的数据发布为只读共享内存段，
   客户端零拷贝直接读取（微秒级）；Master 收到实时行情更新时会同步写入快照尾部，
   因此客户端读到的是准实时数据。
5. **容错降级**：快照未覆盖的证券或 K 线类型自动改走 IPC；IPC 请求失败或响应无法解析时，
   客户端回退到自己的本地数据驱动（日志中出现 ``Fallback to local driver``），
   因此 Master 退出后客户端仍可继续工作。该本地驱动连接在客户端启动时即建立并全程持有
   （兜底用，非按需懒创建）：对 sqlite 开销可忽略，对 MySQL / ClickHouse 则会建立真实连接池。
   不过占大头的 K 线预加载已免除，故前述启动时间与内存占用大幅下降的效果仍然成立。

配置项
------

均位于 ``hikyuu.ini`` 的 ``[hikyuu]`` 节，**缺省即启用**，通常无需手工配置：

::

    [hikyuu]
    tmpdir = /home/user/stock/tmp
    datadir = /home/user/stock
    ; 是否参与单机数据服务协商，设为 False 则本进程始终以独立模式运行
    kdata_server = True
    ; Master 是否发布 K 线共享内存快照，设为 False 则客户端全部改走 IPC 请求
    kdata_server_shm_cache = True
    ; 客户端等待 Master 数据就绪的最长秒数，0 表示无限等待，超时后降级为独立模式
    kdata_server_wait_timeout = 600

.. list-table::
   :header-rows: 1
   :widths: 30 10 60

   * - 配置项
     - 默认值
     - 说明
   * - ``kdata_server``
     - ``True``
     - 是否参与单机数据服务协商。置 ``False`` 时本进程既不竞选 Master，也不连接已有服务，
       行为与本功能引入之前一致。
   * - ``kdata_server_shm_cache``
     - ``True``
     - Master 是否发布 K 线共享内存快照。置 ``False`` 时客户端全部查询改走 IPC，
       延迟升高，但不再占用共享内存。该开关作用于 Master 侧，对所有客户端生效。
   * - ``kdata_server_wait_timeout``
     - ``600``
     - 客户端等待 Master 数据就绪的最长时间（秒），``0`` 表示无限等待；
       超时后客户端降级为独立模式启动，避免永久挂起。

数据获取路径
------------

客户端的每一次 K 线查询按以下优先级选择路径：

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - 路径
     - 适用场景
   * - 共享内存快照
     - Master 已预加载、且该证券未被 ``xxx_max`` 截断的 K 线类型，零拷贝读取，最快
   * - 本地数据驱动
     - Master 未预加载的 K 线类型，以及分时（``TIMELINE``）、分笔（``TRANS``）数据
   * - IPC 请求
     - 快照未覆盖的证券（如被 ``xxx_max`` 截断），以及共享内存不可用时的兜底
   * - 本地数据驱动
     - IPC 请求失败或响应异常时的最终降级

.. note::

    ``[preload]`` 节的配置决定了快照的内容：某个 K 线类型为 ``True`` 才会被 Master
    预加载、才会进入共享内存快照；``xxx_max`` 限制预加载条数，被截断的证券不进快照，
    由客户端改走 IPC 查询（两条路径的结果一致）。

    客户端进程自身的 ``[preload]`` 配置会被自动忽略（全部置为 ``False``）。

    复权处理始终在客户端本地完成，数据服务传输的都是不复权的原始数据。

常见问题
--------

**多个进程之间的数据会不一致吗？**

不会。客户端与 Master 使用同一 ``datadir``，快照与 IPC 返回的都是 Master 已加载的数据，
实时行情的镜像写入保证了准实时一致。

**Master 运行在 Jupyter 中，客户端变慢？**

Master 的 Python 主线程若长时间持有 GIL（例如一段未释放 GIL 的密集计算），服务端处理请求
的线程在写日志时会被阻塞，客户端表现为请求延迟被放大。建议把 Master 放在独立的
Python 进程中运行。

**如何完全关闭该功能？**

在每个进程的 ``hikyuu.ini`` 中设置 ``kdata_server = False``。

**临时目录下会残留哪些文件？**

服务地址与文件锁位于系统临时目录（unix 取环境变量 ``TMPDIR``，缺省 ``/tmp``；
Windows 取系统临时目录），文件名形如 ``hikyuu_kdata_server_{hash}.ipc`` 与
``hikyuu_kdata_server_{hash}.lock``；另有 ``hikyuu_ks.last`` 记录当前共享内存段名，
用于清理上一个异常退出的 Master 的残留段。Master 正常退出时会释放文件锁并删除共享内存段，
锁文件与记录文件本身为空文件，残留后可安全手工删除。
